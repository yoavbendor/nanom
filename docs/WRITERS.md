# Plan: writing with nanom (Parquet first, Lance later)

nanom describes a binary layout once (`describe<T>`, `field<Id, T>`, `be<>`, `ubits<>`), and
that description can drive writing as well as reading. This plan turns the write side into
production code, in the spirit of Rust's deku / binrw (derive read + write from one description)
and cookie-factory (serializer combinators over a sink). The first user is
[nanoarrow2parquet](https://github.com/yoavbendor/nanoarrow2parquet); Lance comes later.

**Rule zero: reading stays exactly as it is.** Encoders live in their own headers that the read
path never includes, so a reader's code, compile time and speed do not change. See
[Reading only](#reading-only-the-short-path).

## Why

- **One description, no drift.** Field ids, types, required / optional and enum values exist
  once. Before this plan, nanoarrow2parquet carried its own 156-line Thrift encoder and built
  `FileMetaData` with hard-coded field numbers: a second copy of
  `nanom/formats/parquet_thrift.hpp` that nothing kept in sync.
- **Much stronger tests in both directions.** Every encoder is checked by a round trip through
  decoders already proven against pyarrow. Every decoder can be fed structurally valid inputs
  generated by encoding random values, which reaches far deeper than random bytes.
- **Lance fits the same model.** Lance metadata is protobuf: tagged like Thrift. A protobuf wire
  codec next to the Thrift one lets one `field<Id, T>` description serve both.

## Design rules

- **Two-way comes from described types, not from combinators.** Combinators such as `alt`,
  `take_while`, Thrift skip-on-mismatch or lenient size checks lose information and cannot be
  inverted. Parsers stay one-way; described types (`field<>`, `list<>`, `lazy<>`, `be<>`,
  `ubits<>`) are two-way.
- **Sinks, not containers.** Encoders write to a byte sink: a growable vector, a fixed span
  (overflow is an error, never a write past the end), a counter (exact size without writing) or
  any type with `bool put(const std::byte*, std::size_t)` (a file, a socket). Small writes are
  staged; large payloads pass straight through.
- **Zero-copy writing.** Strings and binaries are views. Repeated members are written from a
  caller's span (`list<E>::of(span)`) and nested messages from a caller's object
  (`lazy<M>::of(m)`) without copying. Lists and structs decoded from a file are written back
  verbatim.
- **Writing is checked like reading.** A length or count that does not fit the wire type (a
  Thrift `i32`) is an error. A required nested message that was never set is an error. An
  overflowing fixed sink is an error. The encoder reports where (`describe<M>::name()`).
- **Policy stays in the writer.** Page sizes, dictionary fallback and statistics are decisions;
  nanom supplies the codecs and kernels.

## Phases

| phase | work | done when | status |
|---|---|---|---|
| A | Production Thrift compact encoder: `nanom/tagged_encode.hpp` with sinks, exact size, `list<E>::of` / `lazy<M>::of` sources, narrowing and required-message checks. nanoarrow2parquet encodes `PageHeader` / `FileMetaData` from the shared `parquet_thrift.hpp` model and drops its hand-written encoder. | Files round-trip through pyarrow, arrow-rs and parquet2nanoarrow; footers read back identically by all three; write speed at parity with the previous nanoarrow2parquet. | **done** ([results](#phase-a-results)) |
| B | `emit<T>` for fixed-layout described structs (`be<>`, `ubits<>`, arrays), with computed fields (lengths, counts, offsets filled by a size pass or back-patch, like binrw's `calc`). | Every described type in nanom's tests and examples round-trips byte-for-byte. | planned |
| C | Encoding kernels next to the decoders: bit packing, RLE / bit-packed hybrid, DELTA_BINARY_PACKED, BYTE_STREAM_SPLIT, a dictionary builder, statistics; possibly Snappy / LZ4 compression (zstd stays external). | Each kernel round-trips through its decoder and is fuzzed; nanoarrow2parquet gains the encodings it lacks. | planned |
| D | nanoarrow2parquet rebuilt on A–C. A protobuf wire codec in `tagged.hpp` for Lance metadata, then a Lance writer. | Parquet and Lance writing on one base, checked by their reference readers. | planned |

## Phase A in detail

**nanom**

1. `nanom/tagged_encode.hpp` (new; `tagged.hpp` does not include it):
   - sinks: `vector_sink`, `span_sink`, `counting_sink`, and any `byte_sink`;
   - `thrift_compact_encode(m, sink) -> expected<std::size_t, encode_error>`;
   - `thrift_compact_size(m)` (exact, via the counting sink);
   - checks: string, binary and list lengths must fit `i32`; a required `lazy<M>` must be set.
2. `list<E>::of(std::span<const E>)` and `lazy<M>::of(const M&)` in `tagged.hpp`: borrowed
   sources that iterate and decode like decoded ones, so code that inspects a model works on
   both.

**nanoarrow2parquet**

3. Depend on nanom (pinned, header-only). Page headers and the footer are built as
   `nanom_formats::parquet` structs and encoded with nanom. `src/thrift_compact.hpp` is deleted.
   Page headers encode into a stack buffer (`span_sink`), so the per-page cost does not grow.

**Testing, built during the work (not after it)**

- *Round-trip property tests* (nanom): random values of every Parquet model message, with random
  optional fields, strings and lists, are encoded, decoded and compared field by field.
  Re-encoding what was decoded must give identical bytes.
- *Size and sink properties* (nanom): `thrift_compact_size` equals the bytes written. Encoding
  into every too-small `span_sink` fails without writing past it, checked under ASan with
  exact-size buffers.
- *Structured fuzzing* (nanom): the Thrift fuzzer also encodes random messages, mutates the
  bytes and decodes them. Valid inputs must decode to the same value; mutated ones must fail
  cleanly.
- *External oracles* (nanoarrow2parquet): every written file is read by pyarrow, by arrow-rs (the
  Rust `parquet` crate) and by parquet2nanoarrow. Data must equal the input. Footer fields
  (schema, row groups, chunk offsets and sizes, encodings, codec, `created_by`) must agree across
  all three and with what was written.
- *Performance*: the nanoarrow2parquet write benchmark before and after, on the same host.

## Phase A results

Delivered in nanom `9b4751e` (encoder, tests, fuzzing) and nanoarrow2parquet `22bb84a` /
`24edd6f` (the port and the oracle test).

**Correctness**

| check | result |
|---|---|
| nanom round-trip properties: 10 Parquet model messages generated by reflection, a few hundred values each | decode(encode(x)) == x, re-encoding is byte-identical, the size is exact, every too-small buffer fails cleanly (ASan, UBSan). A planted encoder bug fails 7 of 10 message types. |
| nanom structured fuzzing | 200,000 iterations clean; a third of the inputs are generated footers and page headers that must decode back to themselves before being mutated |
| nanoarrow2parquet before vs after | the 12 files its test suite writes are **byte-identical** to the previous hand-written encoder's output |
| `oracle_roundtrip` (nanoarrow2parquet ctest) | 17 files (every supported type, nulls at density 0 / 0.3 / 1, nested structs, several row groups, unicode / long / empty strings, NaN and ±0, zstd and uncompressed). They read back exactly in **pyarrow**, **arrow-rs** and **parquet2nanoarrow**. arrow-rs's footer matches pyarrow's field by field, and the chunks tile the file. A planted one-byte size error produces 594 failures. |
| existing suites | nanoarrow2parquet ctest (incl. the benchmark gate) and the Python bindings' 25 tests pass |

**Reading is unaffected**: footer decode speed in `nm_thrift_bench` is unchanged (old and new are
within run-to-run noise on validate, full walk and single row group), and `tagged.hpp` contains no
encoder.

**Write speed** (`bench_n2p` / `bench_n2p_soa`, previous build vs this one, same host, output on
tmpfs, median of 7 alternating runs; file sizes identical in every case):

| benchmark | case | before | after | speed |
|---|---|---:|---:|---:|
| bench_n2p | zstd, strings, 512 MB in 128 MB chunks | 1.553 s | 1.626 s | 0.96x |
| bench_n2p | uncompressed, 30% nulls, 512 MB in 128 MB chunks | 1.204 s | 1.202 s | 1.00x |
| bench_n2p | uncompressed, 256 row groups (1 MB chunks) | 0.314 s | 0.325 s | 0.97x |
| bench_n2p_soa | zstd, strings | 2.160 s | 2.135 s | 1.01x |
| bench_n2p_soa | uncompressed, 30% nulls | 1.986 s | 1.973 s | 1.01x |
| bench_n2p_soa | 256 row groups | 0.520 s | 0.488 s | 1.07x |

All within this shared host's noise: parity. An earlier run with the output on disk showed 0.77x
on the uncompressed case. Rerun on tmpfs it was 1.01x, so that gap was disk write-back noise, not
the encoder. Encoding the metadata is a tiny share of a write: a 1.4 MB footer (1,000 row groups
x 20 columns) encodes in about 2 ms.

## Reading only: the short path

For code that only reads (and for AI assistants generating such code), include just what you need:

| task | include | entry points |
|---|---|---|
| parse a binary layout | `nanom/nanom.hpp` | combinators, `strct<T>()`, `overlay<T>()` |
| decode Thrift / tagged messages | `nanom/tagged.hpp` | `thrift_compact<M>()`, `list<E>`, `lazy<M>` |
| Parquet footer and page headers | `nanom/formats/parquet_thrift.hpp` | `read_file_metadata`, `thrift_compact<PageHeader>()` |
| decode column pages | `nanom/columnar.hpp`, `nanom/values.hpp`, `nanom/codec.hpp` | see [COLUMNAR.md](COLUMNAR.md) |

None of these includes an encoder. Writing needs `nanom/tagged_encode.hpp` (and, later,
the phase B–C headers).
